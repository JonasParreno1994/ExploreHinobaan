EXPLORE HINOBA-AN TOURISM PORTAL
SYSTEM AUDIT AND RECOMMENDATIONS

Audit result
============

The system is generally well structured. It includes public tourism content,
enterprise onboarding, services and reservations, local products and orders,
tourist verification, enterprise microsites, analytics, notifications, and
security monitoring.

Automated verification completed successfully:

- 254 tests passed
- 1,848 assertions passed


HIGHEST-PRIORITY CHANGES
========================

1. Protect sensitive uploaded files

Enterprise permits, reservation payment proofs, and product-order payment
proofs currently use Laravel public storage. Anyone who discovers a storage URL
could potentially access these files.

Move these files to private storage and serve them through authorized controller
routes:

- Enterprise documents and permits
- GCash payment receipts
- Reservation payment proofs
- Product-order payment proofs

Tourist verification documents already use the safer private-storage pattern.


2. Tighten Administrator and Tourism Staff permissions

Most routes inside the admin group allow both Administrator and Tourism Staff.
This appears to include sensitive functions such as user management, role
management, account deletion, and system settings.

Recommended permission matrix:

- Enterprise verification: Administrator and Tourism Staff
- Tourist verification: Administrator and Tourism Staff
- Tourism content management: Administrator and Tourism Staff
- User management: Administrator only
- Role management: Administrator only
- Security configuration: Administrator only
- Site settings: Administrator only


3. Improve production reliability

The current local configuration uses the database for cache, sessions, and
queues. A recent application error showed a PostgreSQL timeout while checking
the queue/cache table. A slow database could therefore affect sessions, cache,
notifications, queues, and page availability at the same time.

Recommended production configuration:

- Use Redis for cache, sessions, queues, and rate limiting
- Run queue workers under a process supervisor
- Configure automatic database backups
- Add application and database monitoring
- Set APP_DEBUG=false in production
- Add health checks for database, queue, storage, and routing services


4. Add throttling to Enterprise authentication

Tourist login and registration are throttled, but Tourism Enterprise login and
registration do not currently have equivalent route throttling.

Add rate limits to prevent password guessing, registration spam, and repeated
large document uploads.


5. Investigate intermittent frontend initialization errors

The browser log contains an intermittent landing-page Inertia error:

Cannot read properties of null (reading 'page')

Add browser tests covering direct navigation and page refresh for:

- Landing page
- Enterprise microsite
- Local product page
- Interactive map
- Admin dashboard


IMPORTANT WORKFLOW IMPROVEMENTS
===============================

6. Centralize status definitions

Create PHP enums or centralized constants for:

- Enterprise application status
- Product publication status
- Reservation status
- Payment status
- Verification status
- Document status
- Website publication status

This will reduce mismatches between terms such as approved, published, active,

7. Consolidate duplicated notification logic

Admin, Tourism Enterprise, and Tourist notifications contain similar shared
Inertia data, dropdown components, mark-as-read controllers, and 15-second
polling behavior.

Create a shared notification presenter/service and a reusable dropdown base
component. Consider broadcasting or adaptive polling when usage grows.


8. Clarify Services versus Website modules

The interface should clearly communicate that:

- Services & Facilities manages operational and bookable records.
- My Website controls how those records appear publicly.
- Rooms, activities, products, tours, and menus must have one authoritative
  data source.

Add Manage Content links from the homepage section manager to the appropriate
source module.


9. Improve draft and publishing behavior

Add:

- Last published date and publisher
- Unpublished changes indicator
- Draft-versus-published comparison
- Restore previous published version
- Confirmation before unpublishing
- Publishing checklist for logo, cover, location, contact, and required content


10. Improve legacy-enterprise onboarding

Approved enterprises can exist without an enterprise_websites record. Add an
idempotent migration or Artisan command that creates the CMS foundation for all
approved enterprises without overwriting existing websites.

SYSTEM RE-AUDIT - CURRENT FINDINGS
==================================

The system is now feature-rich and its main Laravel architecture is generally
sound. Before adding more major modules, development should focus on publishing
integrity, consistent authorization, browser testing, workflow rules, and
frontend maintainability.

Latest automated verification:

- 273 tests passed
- 1,990 assertions passed


CURRENT HIGHEST-PRIORITY CHANGES
================================

1. Complete Draft and Publish isolation

Publishing currently snapshots the website appearance, SEO settings, and
homepage sections. Gallery images, social links, menus, tours, products,
services, and other specialized content are still read from their current
records.

This means some edits can affect the public microsite without using Publish
Changes. Snapshot or version every website-managed marketing record, or add a
consistent draft/published state to those records.


2. Fix the Homepage Section Manager contract

The CMS allows enterprises to change section titles and subtitles, but public
microsite components generally render fixed headings. Saved headings therefore
do not consistently appear on the public website.

Either pass the configured title, subtitle, and content into every public
section component or remove inputs that have no visible effect.


3. Make the module matrix authoritative everywhere

Some specialized controllers still check exact enterprise type names such as
Cafe, Restaurant, Tour Guide, or Tour Operator. This weakens the flexible
Administrator-managed module matrix and makes future enterprise types harder to
support.

All module navigation, forms, routes, and backend authorization should use the
EnterpriseWebsiteModuleRegistry capability checks.


4. Finish browser-test configuration

Feature tests pass, but the browser-test environment previously failed because
its SQLite database did not contain required tables such as banners.

Add a repeatable browser-test workflow with:

- A dedicated .env.dusk.local configuration
- Automatic test database migration
- ChromeDriver and application server startup
- Browser tests in continuous integration
- Direct-navigation and refresh coverage for public, partner, and admin pages


5. Improve analytics integrity

The analytics endpoint validates event types and is throttled, but clients can
still submit arbitrary target IDs and labels. This can distort most-viewed
reports.

Add:

- Validation that the target belongs to the requested enterprise
- Duplicate-event suppression
- Bot and crawler filtering
- A defined analytics retention period
- Aggregation of older raw events


6. Centralize workflow transitions

Reservation and product-order status transitions are spread across multiple
controllers. Move allowed transitions and side effects into enums, actions, or
workflow services so inventory, notifications, analytics, and audit history
remain consistent.

FEATURES AND DUPLICATION TO OMIT OR CONSOLIDATE
===============================================

1. Do not create duplicate operational content

Rooms, services, products, menus, tours, and activities should each have one
authoritative data source. My Website should control visibility, presentation,
ordering, and featured selection instead of copying the records.


2. Do not display two enterprise sidebars

Keep one Partner Workspace sidebar. My Website should be an expandable section
or use nested navigation within the same sidebar.


3. Remove ineffective CMS fields

If a configurable heading, subtitle, or content field is not rendered on the
public microsite, connect it to the public component or remove it.


4. Avoid premature specialized modules

Do not add new tables for Dive Center, Transport Provider, Farm Tourism Site,
or other future types until reusable modules and the feature matrix cannot
represent their requirements.


5. Decide whether product ordering supports a cart

The workflow is primarily single-product even though an order-items structure
exists. Either implement genuine multi-product cart checkout or simplify and
clearly label the workflow as single-product ordering.


6. Clarify manual refunds

If no payment provider confirms a refund, use the label Marked as Refunded and
require notes, an external reference, the responsible user, and a timestamp.
